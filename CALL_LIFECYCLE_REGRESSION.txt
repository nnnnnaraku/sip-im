1. Actual baseline defects
- A global Dialog and INVITE ClientTransaction were reused by all calls.
- Every successful INVITE response/incoming acceptance created a sleeping auto-hangup thread.
  It later called unqualified hangup(), so an old timer could end a new call.
- Every 200 OK could restart media/timing; hangup before establishment attempted BYE rather
  than performing the INVITE CANCEL flow.
- Busy/reject/error/timeout and DialogTerminated paths did not finish the matching call.
- Authentication retried with a fresh Call-ID, From tag and mutable selected contact.
- Media allocation errors were swallowed; partly allocated sockets/devices could survive.
- Microphone workers read shared mutable device fields; video UDP interrupt did not unblock receive.
- Conference startup could leak the first socket when allocating the second socket failed.

2. State and ownership
New independent classes:
  CallState: DIALING, RINGING, ACCEPTED (incoming 200 sent, waiting for ACK),
             ESTABLISHED, ENDING, ENDED.
  CallSession: unique application UUID; SIP Call-ID; immutable peer/direction/video/room;
               current INVITE CSeq/branch; timestamps and terminal reason.
  CallLifecycleManager: single active slot, guarded transitions, exactly-once media/cleanup,
                        injectable Scheduler/clock, cancelled-task removal and bounded history.

Normal outbound:
  begin -> DIALING -> provisional/RINGING -> valid 2xx -> ACK -> ESTABLISHED
  -> media once -> one auto-hangup -> BYE/remote BYE/failure -> ENDED.
Normal inbound:
  INVITE -> RINGING -> tagged 200/ACCEPTED -> matching ACK -> ESTABLISHED -> media once.
Active peer and media intent are independent of the currently selected chat contact.

SipVideoCallClient retains JAIN objects in a per-call binding; request matching includes
Call-ID, local/remote tags, INVITE CSeq and transaction/branch where available.
Unknown BYE/CANCEL or wrong tags return 481 instead of ending the active call.
A second independent incoming call returns 486. Existing in-dialog renegotiation is rejected
with 488, keeping the original call. Duplicate initial INVITE replays its cached final result.
This is a single simultaneous SIP call client, not a new call-waiting/re-INVITE framework.

3. Timers and signalling races
- The scheduler is a daemon ScheduledThreadPoolExecutor with remove-on-cancel enabled.
- Every timer captures a CallSession and registration; cancelled/already-fired/stale callbacks
  are ignored, and the SIP adapter rechecks identity after acquiring the same lifecycle monitor.
- Local hangup releases the active slot and physical media without waiting for remote responses.
  The old binding stays available for late signalling; immediate redial can use a fresh Dialog.
- Before any provisional response, CANCEL intent is recorded but not sent. The first matching
  1xx sends one CANCEL for the original transaction.
- An INVITE 2xx winning the CANCEL race is ACKed, then BYE'd, without starting old media.
- Every repeated valid 2xx is ACKed; media and timer are not allocated again.
- Other fork dialogs are ACKed/BYE'd and never replace the primary media.
- An already established call ignores late INVITE provisional/error/transaction-timeout events.
  A failed duplicate/fork ACK or fork BYE does not end the healthy primary dialog.
- Incoming local hangup after 200 but before ACK waits for ACK before BYE. A retained end timer
  handles missing ACK, scoped to that old binding even while another call is active.
- Incoming ACK timeout closes its confirmed dialog with BYE; repeated or malformed ACK does
  not create media. Authentication preserves request identity and is limited to two retries.
- MESSAGE/file dispatch remains outside the lifecycle monitor; signalling serialization does
  not newly hold that lock during ordinary message/file reassembly or disk writes.

4. Media changes (ownership only, no codec/protocol redesign)
- Startup failure is propagated to the lifecycle adapter; partial resources are unwound.
- stopMedia performs physical cleanup only. Statistics and UI end notification belong to
  finishCall(session), so an old call cannot finish the next call's log record.
- Microphone/video/level-monitor callbacks capture their own session and device objects.
  A stopped old worker cannot adopt a new sender/camera/window via shared fields.
- Audio receiver constructor failure closes the UDP socket and partial speaker allocation.
  Stop closes receive socket before joining; it never waits in speaker.drain().
- Microphone runs bind their own line/listener; line/speaker closure is once per lifetime.
- Video receiver stop closes its socket to release blocked DatagramSocket.receive().
- ConferenceVideo rolls back partial startup, stops a partly opened camera before receive-only
  fallback, closes both sockets and ends workers. A stopped instance cannot be restarted.
- Existing camera-unavailable receive-only behavior is retained.
- Logs identify application UUID/Call-ID/CSeq/state/peer and termination reason, with bounded
  identifiers and no authentication contents. Media-stop logs retain packet/frame counters.

  call.invite.timeout.sec=64

9. Known limits
- Exactly one simultaneous SIP call; no call waiting, transfer, hold or general re-INVITE support.
- Automatic answer remains enabled; no new manual accept/decline UI is added.
- Up to64 call bindings are retained. Beyond bounded history, a late valid stack-owned Dialog
  can still be ACKed/BYE'd without claiming media; no unbounded historical call store is added.
- JAIN SIP handles normal transaction retransmission. Automated proxies do not prove stack,
  NAT, miniSIPServer callback behavior, real codec interoperability or real hardware release.
- IOExceptionEvent has an endpoint, not reliable call identity. It is logged, while scoped
  transaction/application deadlines handle teardown; a shared-proxy I/O error does not kill
  an unrelated active dialog.
- Slow synchronous Web SSE/UI callbacks can still delay the lifecycle monitor. Bounded
  asynchronous Web delivery is a separate task; MESSAGE/file disk work is not under that lock.
- Driver/native calls may hang despite close/interrupt. Workers use bounded joins and are
  fenced from new session resources; this is not a guarantee against a defective native driver.
- A BYE send failure releases local media/slot, but cannot guarantee remote teardown until
  transport recovery/server expiry. Tests prove local ownership, not remote delivery.
- This branch does not contain the independent audio, Web, file, group or camera diagnostics fixes.
