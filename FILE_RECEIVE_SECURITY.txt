文件接收安全与边界校验
分支 fix/file-receive-security
基于 main@1cc201761921ddb668f159741c87df5ace7d35b6
本分支不包含群聊、音频 P0 或视频诊断改动。

问题与实现
1. 旧 SIP 接收端将远端 Base64 文件名直接拼到 received 下，Files.write可越界/覆盖；
   fileId单独作为缓存key、任意total预分配列表、无总量/超时边界；错误后仍回SIP200。
2. 旧 Web 上传无界readAllBytes、同名覆盖；下载对路径做basename修剪而不是拒绝；
   SSE把原名直接作为URL，安全随机落盘后必须同步修正。
3. ReceivedFileStore统一处理接收和Web上传：验证原名，仅把它作为显示/协议元数据；
   UUID+安全后缀为落盘名，CREATE_NEW创建隐藏.part，完整流写/SHA256后无覆盖发布。
   普通失败清理本次临时文件；不删除、不重命名用户旧文件。
4. FileTransferReceiver使用(sender,id)隔离，严格UTF8/Base64、索引/元数据一致性与重复指纹。
   只在完整保存成功后才返回complete并产生附件事件；非法数据返回400/409/413/507等。
5. FileMessageSender流式Base64，固定本次收件人；最后一片必须在源长度/身份校验和编码完成后发出。
   零字节发送一条total=1、空数据的原格式帧。不存在/超限/发送异常明确抛错。
6. FileHttpApi使用流式上传/下载、唯一存储名URL、严格参数/路径、GET/HEAD/POST方法边界，
   无效路径不“修剪后成功”，不把未完成文件提供为下载；响应提交后发生IO失败直接中断。
   原名通过SSE name显示，URL由存储名生成；未知类型attachment+nosniff+CSP，防同源脚本执行。
7. VIDEO消息不再自动Desktop.open，防伪装类型的可执行文件自动运行；网页播放和人工打开保留。
   WAV消息保持原播放入口；录制的发送文件也经安全存储，临时WAV在finally清理。

协议兼容
原协议不变：
 #FILE|IMG或VOICE或VIDEO|fileId|UTF8文件名Base64|从0开始index|total|Base64数据
保持text/plain SIP MESSAGE与原字段个数，既有非空合法分片和乱序组装可继续使用。
原始文件名不被替换成随机存储名发送。新fileId为UUID，旧客户端将其作为普通id处理。
增加的边界会明确拒绝旧版曾接受的危险/超限输入；不是协议字段升级。
SIP每片200不等于文件级端到端成功。HTTP ok=true/status=SUBMITTED只表示本地分片提交，
没有新增文件ACK、重传/取消/持久恢复协议。接收完整性的SHA256需与发送端实际样本比对；
原wire无整体哈希或签名，不能声称检测所有在途篡改。

生产硬边界（默认无法通过配置提高）
 接收目录：本进程工作目录/received；不接受远端目录字段，实例靠独立cwd隔离
 文件名：UTF8最多240字节，拒绝分隔符、绝对/盘符/UNC/ADS、控制/格式字符、
 非法surrogate、尾点/尾空格、Windows保留设备名(含大小写/扩展名/上标设备号)及危险编码形式
 每文件：16MiB；目录：256MiB、512个文件，含已有文件及临时文件；不自动清理旧成果
 每SIP文件body：8192B；每片：4096个Base64字符；每文件：32768片；活动传输：8
 分片数据预算：64MiB (UTF16字符2字节+每片估算开销128字节)
 终态/摘要预算：16MiB、活动及终态ID合计最多256；满时507，不提前淘汰未过期记录
 空闲：120秒无新片；绝对传输寿命：1小时；清理线程30秒检查，失败/关闭释放状态
 已完成及拒绝ID的终态窗口：1小时；已完成同片重传验证摘要但不再次发布/落盘
 零字节：允许；default800字符分片支持16MiB；过小自定义chunk造成total超限则拒绝
 内存预算是受控数据/结构估算，非整个JVM堆的精确上限

路径防护与实际限制
- 根目录及每级祖先验证NOFOLLOW、realpath和身份，拒绝符号链接/junction/reparse；
  文件打开NOFOLLOW，写前/完成后及读流close再次验证root/filekey/大小，禁止覆盖。
- Java 8 Windows标准库缺少目录句柄相对原子打开/重命名，仍有恶意本机并发替换的TOCTOU窗口。
  根目录及祖先必须由OS权限保护，不给不可信本机用户写权限；本轮未改ACL或防火墙。
  不能宣称已经防御拥有本机写权限的攻击者的所有竞态/硬链接操作。
- 常规异常、超限及元数据冲突自动清理；进程被强杀或未能取得临时文件身份时可能残留隐藏.part。
  它们不能下载/不会触发完成事件；为避免删错他人的替代文件，需停止相应实例后人工核查，
  本实现不会猜测并删除旧received文件或其他进程的临时文件。
- 旧目录存在不安全链接、子目录或超过限额时会阻断新保存；由负责人备份归档后处理，
  不通过提高限制、自动删除、跟随链接或重置工作区来绕过错误。
- UTF8/Windows规则有意更严格，部分含格式控制/危险编码的旧文件名不再支持。
- HTTP仍继承原可信局域网部署，无用户鉴权/慢请求超时改造；本轮不将其宣称为公网生产安全。
- HTTP未新增Range（旧实现也没有）；小型视频文件浏览器完整下载播放待真实回归。
- 同一sendFile传输收件人固定；长HTTP上传过程中改变联系人，仍按sendFile开始时联系人发送，
  未引入新的Web收件人参数。用户应在文件提交前保持联系人不变。
- 去重为内存窗口，重启或1小时后不能提供持久去重，但每次新落盘仍唯一且不覆盖。
- 不修改音视频编解码、会议、miniSIPServer、VideoRelay、账号密码或防火墙。
  因从main独立开发，已有音频缺陷不会由本分支解决。

独立人工验收（以下本轮全部NOT_RUN）
须另行获准使用既有SIP服务器。两个客户端使用本分支同一JAR及各自私有配置/独立cwd。
保留原包，不执行setup-mss、不改账号/会议室/防火墙，不抢占其他工作线账号绑定。
1. 文字消息双向正常；接收端真实收到新图片/WAV/MP4，发送端/接收端SHA256和大小一致。
2. 中文、空格、%、&、#、+原名显示正常；/files URL用UUID存储名，不直接含原名。
3. 同名图片发送两次，接收端留下两个不同UUID文件，原有同名文件字节和哈希不变。
4. 零字节文件只有一个空数据分片，真实保存0字节；UI对空图片/音频不能播放是媒体内容无效，
   不应将这一点误判为文件传输失败。不要为了播放零字节而改测试断言。
5. Web上传超16MiB/危险名被400/413拒绝，received无完整结果；原有文件不变。
   不向现用服务器注入非法SIP包；遍历/UNC/设备名/畸形chunk优先用自动夹具验。
6. 在专用临时接收目录中放junction/symlink后仅跑离线store测试，确认拒绝；
   不对真实received或服务器创建测试链接，不用修改防火墙模拟失败。
7. 传一部分后停止发送，未被其他IO阻塞时通常120秒+最多30秒检查后缓存超时；无完成附件/可下载半文件；
   如强杀进程留下.part，标记实际限制并保留证据，不把残留当完整文件。
8. 重复同片不产生第二次附件；冲突片失败；同ID不同sender不混。真实重放无授权夹具则NOT_RUN。
9. 图片显示、WAV播放、MP4播放/下载和旧合法文件URL回归；未知类型下载不当网页执行。
10. VIDEO不自动启动系统程序属于安全行为；用户确认后仍可网页播放。
11. 文件发送期间切换联系人，已开始的同一传输全部分片仍投递原收件人。
12. 点对点通话、会议/视频中继与后台仅在后续授权合并回归中检查；本轮没有启动这些服务。
